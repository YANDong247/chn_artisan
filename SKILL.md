# Skill: Commit code to a remote GitHub repository

Purpose
-------
This skill captures a concise, repeatable workflow for preparing and pushing local code changes to a remote GitHub repository (example target: https://github.com/YANDong247/chn_artisan.git). It's intended for workspace-scoped use by agents and humans collaborating in this repo.

When to run
-----------
- You have local changes in the workspace that should be committed and pushed.
- You want a safe, checklist-driven process that avoids leaking secrets and produces clean commits.

Step-by-step workflow
---------------------
1. Inspect the workspace diff and uncommitted files.
   - Command: `git status --porcelain -uall` and `git diff --staged` (if any).
2. Identify what to include in the commit.
   - Decision: commit all changes vs stage specific files.
   - Quality check: exclude secrets or large binaries; respect `.gitignore`.
3. Choose branch and remote.
   - Default: branch = `main` (confirm if repo uses `master` or other branch).
   - Remote: `origin` should point to the provided repository URL.
4. Write a clear commit message.
   - Format recommendation: `<area>: short summary

  Longer description (optional, short bullet list of changes)`
5. Run pre-push checks.
   - Optional: run unit tests, linting, build steps.
6. Commit and push.
   - `git add` selected files
   - `git commit -m "<message>"`
   - `git push origin <branch>`
7. Verify remote state.
   - `git ls-remote --heads origin` or check the repository web UI.

Decision points & branching logic
---------------------------------
- If there are secrets detected (e.g., API keys), stop and remove them from the commit; use environment variables or GitHub Secrets instead.
- If the target repo requires a PR (protected branch), push to a feature branch and open a pull request instead of pushing to `main`.
- If there are large files, consider using Git LFS or excluding them.

Quality criteria / completion checks
----------------------------------
- Commit contains only intended files.
- Commit message follows the format and describes why, not just what.
- Automated checks (tests/lint) pass locally if required.
- No credentials or secrets present in the commit history.
- Remote push succeeded and branch is updated.

Commands & templates
--------------------
- Inspect changes:
  - `git status --porcelain -uall`
  - `git diff --name-only`
- Stage and commit (all):
  - `git add -A`
  - `git commit -m "chore: short summary of change"`
- Stage specific files:
  - `git add path/to/file1 path/to/file2`
- Push to remote branch `main`:
  - `git push origin main`

Security notes
--------------
- Always scan for secrets before committing. Example quick check using `git`:
  - `git grep -I --line-number "API_KEY\|SECRET\|TOKEN" -- .`
- If secrets are found, remove them and use `git rebase -i` or `git filter-repo` to purge prior history (advanced).

Ambiguities to confirm (questions for user)
-----------------------------------------
1. Which branch should I push to? (default `main`)
2. Do you want all local changes included or a selective commit?
3. Should I create a new branch and open a PR instead of pushing directly?
4. Will you authenticate interactively (GitHub CLI `gh`) or provide a token?

Iteration guidance
------------------
1. Draft the commit locally and run tests/lints.
2. If protected branch or CI required, push to a feature branch and create a PR.
3. After push, confirm remote updates and CI status.
